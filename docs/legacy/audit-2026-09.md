# Legacy audit, September 2026: what went wrong and the rule we follow now

Date: 2026-09-13.
Scope: the first version of PolluxKart, now in `legacy/`.

This file is a "do not repeat" list.
Each section names a problem found in the old code, explains why it matters, and states the rule the rebuild follows instead.
File paths point into `legacy/`, so you can read the original code.

## Glossary

- **API (Application Programming Interface):** the set of web addresses the frontend calls to read or change data.
- **Endpoint:** one of those addresses, for example `POST /api/orders`.
- **Authentication:** checking who someone is, for example by password.
- **Authorization:** checking what that person is allowed to do, for example "only admins can edit products".
- **JWT (JSON Web Token):** a signed piece of text that proves who is logged in.
- **OTP (One-Time Password):** a short code sent by SMS or email that works once.
- **Transaction:** a group of database changes that either all happen or none happen.
- **Race condition:** a bug where two things happen at the same moment and the result depends on which finished first.
- **Idempotent:** safe to repeat; doing it twice has the same effect as doing it once.
- **Webhook:** a web request a payment provider sends to our server to report an event, such as "payment captured".
- **HMAC signature:** a code computed from a message and a shared secret, used to prove the message was not forged.
- **XSS (Cross-Site Scripting):** an attack where a malicious script gets saved on a site and runs in visitors' browsers.
- **IDOR (Insecure Direct Object Reference):** a bug where changing an id in a request lets you see someone else's data.
- **CORS (Cross-Origin Resource Sharing):** browser rules for which other websites may call an API.
- **Paise:** one hundredth of a rupee.

## 1. Security

### 1.1 Anyone could reset anyone's password

`POST /api/auth/reset-password` accepted an email or phone and a new password, with no proof of ownership.
See `legacy/backend/routes/auth.py:37` and `legacy/frontend/src/pages/AuthPage.jsx`.
Combined with a public endpoint that listed admin emails (`legacy/backend/routes/admin.py:131`), an attacker could take over the admin account in two requests.

**Rule:** a password reset needs a single-use token sent to the account's verified email.
The token is stored only as a hash, expires in 30 minutes, and using it logs out every session.
Responses look identical whether or not the email exists.

### 1.2 Debug and setup endpoints shipped to production

`GET /api/otp/debug/{phone}` returned the current OTP for any phone (`legacy/backend/routes/otp.py:134`).
The first-admin setup endpoint had a hard-coded default key (`legacy/backend/routes/admin.py:36`).
`DELETE /api/admin/cleanup/seed-data` wiped orders from a single call (`legacy/backend/routes/admin.py:494`).

**Rule:** no debug, setup, or data-wiping endpoints exist in the API.
The first admin is created by a one-off command run on the server, and that run is written to the audit log.

### 1.3 Admin actions were open to every logged-in user

Creating, editing and deleting products and categories, changing order status, and adjusting stock only checked that the caller was logged in, not that they were an admin.
See `legacy/backend/routes/products.py:21`, `:64`, `:85`, `:97`, `legacy/backend/routes/orders.py:76` and `legacy/backend/routes/inventory.py:24`.

**Rule:** every admin endpoint lives under `/api/v1/admin/`, and the security configuration requires the admin role for that whole path.
A generated test calls every admin endpoint as a normal customer and expects a refusal.
The "second door" rule applies: if one path to some data is guarded, every other path to the same data needs the same guard.

### 1.4 Roles and disabled accounts were trusted from the token

The user's role was copied into the JWT at login and never re-checked.
A demoted or disabled user kept their access until the token expired, up to 24 hours later.
The token was stored in `localStorage` (`legacy/frontend/src/services/apiConfig.js:61`), where any script on the page can read it.

**Rule:** sessions are a random token in an `httpOnly` cookie, which page scripts cannot read.
The server stores only a hash of it and loads the user on every request, so a role change or a disabled account takes effect immediately.

### 1.5 Password hashes leaked from the admin users list

The query removed a field called `password`, but the stored field was `password_hash`, so hashes were returned.
See `legacy/backend/services/admin_service.py:374` and `:398`.

**Rule:** API responses are built from an explicit list of allowed fields (a response class), never by removing fields from a database record.

### 1.6 The payment webhook could not be trusted

The webhook signature was computed over `str(payload)` instead of the exact bytes received (`legacy/backend/services/payment_service.py:173`), so real Razorpay webhooks failed.
If the secret was not configured, the check was skipped entirely.
Payment verification also skipped the signature check when keys were missing, and never compared the paid amount with the order total.

**Rule:** the HMAC is computed over the raw request bytes and compared in constant time.
Missing configuration stops the app from starting instead of skipping checks.
After a signature passes, the server fetches the payment from Razorpay and confirms amount, currency and capture status.
Each webhook event is stored by its id, so a repeated event changes nothing.

### 1.7 Uploads allowed stored XSS

The upload code trusted the file type the browser claimed and the file name's extension, then served files from the API's own address.
An HTML file labelled as `image/png` would be served and run as a web page.
See `legacy/backend/routes/admin.py` (upload handlers) and `legacy/backend/services/s3_service.py`.

**Rule:** uploads go straight to S3 with size and type limits.
The server then reads the file's first bytes to confirm it really is JPEG, PNG, WebP or AVIF (never SVG), and serves images only from a separate media domain.

### 1.8 Other gaps

- CORS allowed every origin together with credentials (`legacy/backend/server.py:73`).
- No rate limiting, so login and OTP could be guessed at speed.
- Search built database regular expressions from raw user input.
- OTP codes came from a non-cryptographic random generator and were printed to logs.
- The frontend loaded Emergent scripts in production (`legacy/frontend/public/index.html:24`) that forwarded console logs and failed response bodies to any page framing the site.

**Rules:** the frontend and API share one origin, so no CORS is needed.
Rate limits protect login, password reset, verification emails and order creation.
Search uses PostgreSQL full-text search with parameters, never string-built queries.
Only first-party scripts load, and a Content Security Policy blocks the rest.

## 2. Secrets

Configuration files with real credentials were committed to this public repository in early 2026.
Git history keeps them even after the files were deleted.

**Rules:**
- `.env` files are never committed; `.gitignore` blocks them.
- `gitleaks` scans every commit in a pre-commit hook and in CI.
- Production secrets live in AWS SSM Parameter Store and reach the server at deploy time.
- Any secret that ever touches git is treated as public and rotated the same day.

## 3. Money, stock and orders

### 3.1 Stock could be sold twice

Order creation read the available stock, then later added to the reserved count with an unconditional update, with no transaction in between.
See `create_order` in `legacy/backend/services/order_service.py`.
Two shoppers buying the last unit at the same moment could both succeed.

**Rule:** stock is reserved with one conditional database update:
`UPDATE inventory SET reserved = reserved + n WHERE sku_id = ? AND on_hand - reserved >= n`.
If no row changes, the item is out of stock.
Database CHECK constraints make negative stock impossible.
A test with 50 parallel buyers and 5 units must produce exactly 5 orders.

### 3.2 Reservations never ended

Cash on delivery orders and abandoned online payments held stock forever.
Cancelling a paid order released stock that had already been consumed, and issued no refund.

**Rule:** every reservation has a status and an expiry time.
A scheduled job releases expired reservations, after checking with Razorpay that no payment arrived.
The order state machine decides what each cancellation does to stock and money.

### 3.3 Double submit created duplicate orders

Nothing stopped the same checkout from being submitted twice.

**Rule:** creating an order requires an idempotency key, so a repeated request returns the first order instead of creating a new one.

### 3.4 Totals were computed in three different places

The cart page, checkout page and backend each calculated shipping and tax on their own.
For example, the browser charged ₹49 shipping and made it free only above ₹500, while the backend charged ₹50 and made it free at exactly ₹500.
The browser also added a flat 18% tax of its own.
The amount on the pay button could differ from the amount charged.
Promo codes were hardcoded in the browser and never applied to the order.

**Rule:** one backend endpoint produces the quote: prices, discounts, shipping, GST split and total.
The frontend only displays it.
Placing an order sends the total the shopper saw; if prices changed, the server refuses and returns the new quote.

### 3.5 Money and time were stored loosely

Amounts were floating-point numbers, which cannot store paise exactly.
Timestamps were a mix of text strings and real dates, so date queries silently missed records.
No unique indexes existed, so duplicate emails, carts and order numbers were possible.

**Rules:** money is stored as whole paise in `BIGINT` columns.
Timestamps are `timestamptz`.
Uniqueness and valid ranges are enforced by database constraints, not only by code.

### 3.6 Tax was not GST-ready

A flat 18% was applied to every product, with no HSN code and no CGST, SGST or IGST split.

**Rule:** each product carries its HSN code and GST rate.
Tax is split into CGST and SGST for same-state delivery and IGST otherwise.
Invoices use a gapless number sequence per financial year.

## 4. Frontend and shopper trust

- **Mock data in production:** the homepage used `legacy/frontend/src/data/products.js` (`legacy/frontend/src/pages/HomePage.jsx:10`), with products that did not exist in the database.
  **Rule:** no mock data in the app; tests use fixtures shaped like the real API.
- **Fake addresses:** checkout used hardcoded addresses such as "John Doe" in Mumbai (`legacy/frontend/src/pages/CheckoutPage.jsx:81`), and those went into real orders.
  **Rule:** addresses come only from the shopper's saved address book.
- **Fake reviews and ratings:** products without reviews showed invented reviews and a default 4.5 rating (`legacy/frontend/src/pages/ProductPage.jsx:107`, `:183`, `:283`).
  **Rule:** only real, verified-purchase reviews are shown; no rating is shown when there are none.
- **No legal pages:** footer policy links pointed to `#` (`legacy/frontend/src/components/layout/Footer.jsx:18`).
  **Rule:** privacy, terms, returns and refunds, cancellation, shipping, warranty, contact and grievance pages exist before payments go live.
- **Touch users could not add to cart from listings:** buttons appeared only on mouse hover.
  **Rule:** every action is visible and reachable by touch and keyboard.
- **Accessibility:** icon buttons had no labels, buttons were nested inside links, and white text on the teal brand colour failed contrast rules.
  **Rule:** automated accessibility checks run in CI, and a test measures colour contrast for every design token pair.
- **Performance and SEO:** one 775 KB JavaScript bundle, no lazy-loaded images, and a single page title for the whole site.
  **Rule:** server-rendered pages with per-product titles, link previews and structured data, plus performance budgets checked in CI.

## 5. Operations and repository

- **No real tests of the risky parts:** tests called a running server, depended on seeded data, and skipped themselves when data was missing.
  Nothing tested payments, stock races, or that customers are refused admin actions.
  **Rule:** integration tests start a real PostgreSQL in a container, and concurrency, webhook replay and authorization tests are required.
- **Debug prints and unstructured logs**, including personal data.
  **Rule:** structured JSON logs with a request id, and no personal data in logs.
- **Health check always said "healthy"**, even when the database was down.
  **Rule:** separate liveness (process running) and readiness (database reachable) checks.
- **Four overlapping CI workflows** triggered on a branch that did not exist.
  **Rule:** one `make ci` target that runs locally and in GitHub Actions.
- **Tracked junk:** test reports, uploaded images, scripts pointing at dead preview servers, and a builder's git identity.
  **Rule:** a clean `.gitignore`, and generated output is never committed.
